Rules and Checks

Every finding rule, severity, threshold, and operational check implemented by QA Sentinels.

About this register

This register describes every finding rule and operational check implemented by QA Sentinels 1.4.2. Rules are code, not policy prose: the linked module is the authoritative implementation.

Severity model

Severity Meaning Automatic action
critical Crash ownership, data-integrity, security, hardware, or fault-core condition requiring review May queue a layer-2 deep trace when QA_DEEP_AUTO=1; boot findings are not traced
error A service, route, privilege, or expected system state is broken Ticket drafting; no automatic deep trace
warning Degraded, non-critical, stale, or coverage-limited state Ticket drafting; no automatic deep trace
info Preflight, status, or capability check only Not stored as a finding

Findings are deduplicated by fingerprint. Repeated journal rules are grouped by a stable signature and show an occurrence count. critical findings do not automatically submit tickets; drafts remain human-reviewed.

Process-path findings are resolved automatically when the process disappears. Audit findings depend on the QA audit rules in root/audit/qa-security.rules. Capabilities held only in a child user namespace, such as Chromium's sandboxed zygote, are namespace-scoped and are not host capabilities.

Scoped policy selectors

allowed_elevation_chains and allowed_cap_processes accept exact process selectors: exe, exe_basename, uid, parent_comm, parent_uid, cap_eff, cgroup_contains, and cmdline_contains. The packaged policy uses them only for the documented libvirt dnsmasq root DHCP-script helper, LXD bridge dnsmasq capabilities, and GDM's user-manager CAP_WAKE_ALARM. There is no general dnsmasq elevation-parent or capability allowlist.

Operational checks without finding severity

  • qa preflight checks the C sampler, journal read access, coredump access, crontab, free disk, fault-core integration, Ubuntu compatibility, unprivileged posture, fault-core triage directory, network inventory, layer-2 state, and eBPF build state.
  • qa status reports last sample/ingest/crash-feed/inventory/hardware/LSM/network times, hardware tier, fault-core state, inventory, evidence, ticket drafts, triage, layer-1 counts, boots, shutdown capture, correlation, raise gate, holds, notifications, layer-2, eBPF, and posture.
  • qa compat --strict checks the supported Ubuntu baseline.
  • qa legal --check checks the legal register and document set.
  • qa platform reports platform capabilities and finding namespaces.
  • qa crosscheck compares drafts on disk with currently reproducible issues and reports drift; it is a review signal, not a severity finding.
  • qa hardware check reports missing required tools and scoped-out sources; it exits non-zero for a missing required source.

Rule lifecycle

  1. Collect: journal, crashes, samples, hardware, LSM, security, network, boot and fault-core data.
  2. Classify: apply the rule tables above; attach fingerprint, severity, subject, detail, and case association.
  3. Deduplicate: update an existing fingerprint's last_ts/count; create a new finding only for a new fingerprint.
  4. Escalate: critical findings may queue a layer-2 request, respecting QA_DEEP_AUTO and QA_DEEP_REQUEST_COOLDOWN_S.
  5. Draft: findings become vendor/local ticket drafts; nothing is submitted automatically.
  6. Notify: staged raise/ tickets and ready correlations can queue desktop notifications; draft digests are intentionally silent.
  7. Resolve: hardware, LSM, security, runtime and coverage findings resolve when their condition clears; boot and journal findings remain for review.
